# opencode-mtls

OpenCode v2 provider plugin for LLM endpoints protected by mutual TLS.

The plugin discovers models over mTLS, then registers them against OpenCode's native provider stack. Inference does **not** go through the Vercel AI SDK: OpenCode's native provider talks HTTP/SSE to a capability-protected loopback bridge, and the bridge forwards the request to the configured HTTPS endpoint using Bun's client-certificate TLS support.

Client certificate material stays in files on disk; OpenCode configuration contains only paths.

## Install from the private GitHub repository

Make sure normal Git access to the private repository works first:

```bash
gh auth login
gh auth setup-git
git ls-remote https://github.com/essinghigh-org/opencode-mtls.git
```

Then reference the Git repository directly from `opencode.jsonc`:

```jsonc
{
  "plugins": [
    {
      "package": "github:essinghigh-org/opencode-mtls#master",
      "options": {
        "providers": {
          "codex-proxy": {
            "name": "Codex Proxy",
            "baseURL": "https://llm.example.com/v1",
            "tls": {
              "certFile": "~/.config/opencode/mtls/client.crt",
              "keyFile": "~/.config/opencode/mtls/client.key"
            }
          }
        }
      }
    }
  ]
}
```

No model list is required in OpenCode config. At startup the plugin requests `/v1/models` over mTLS and creates the provider/model inventory automatically.

## Native OpenCode provider path

For discovered Responses models, the plugin registers:

```text
@opencode/ai/providers/openai/responses
```

For ordinary OpenAI-compatible Chat Completions models, it registers:

```text
@opencode/ai/providers/openai-compatible
```

This means Responses behavior comes directly from the same native OpenCode 2.0 protocol implementation used by OpenCode itself, including:

- streamed Responses parsing and incremental output;
- stateless history replay;
- `store: false`;
- `reasoning.encrypted_content` replay;
- reasoning-summary streaming;
- tool and hosted-tool event handling supported by OpenCode's native provider;
- native Responses error handling;
- OpenCode's native compaction/checkpoint implementation when enabled by OpenCode policy;
- native reasoning-effort request lowering.

The mTLS bridge forces OpenCode's native provider to the HTTP/SSE transport. OpenCode's ChatGPT integration normally prefers its native WebSocket transport, but the protocol/request/response implementation is the same native Responses stack. The plugin does not implement a separate AI SDK translation layer.

## Loopback mTLS bridge

Bun's client-certificate TLS support is attached at a process-local HTTP bridge:

```text
OpenCode native provider
        |
        | HTTP/SSE
        v
127.0.0.1:<ephemeral port>
        |
        | HTTPS + client certificate
        v
configured baseURL
```

Each bridge binds only to `127.0.0.1` on an ephemeral port and requires a random per-process capability header generated by the plugin. Requests without that capability return `403`. The capability header is stripped before forwarding upstream.

This avoids placing non-cloneable functions or TLS objects in OpenCode provider state while leaving OpenCode in full control of protocol semantics.

The bridge also normalizes a current ChatGPT Codex quirk where streamed SSE responses can be labelled `text/plain`; successful requests with `stream: true` are presented back to OpenCode as `text/event-stream` without buffering the response body.

## Enhanced discovery

The normal OpenAI list envelope is supported. Extra fields are optional:

```json
{
  "object": "list",
  "data": [
    {
      "id": "qwen-3.8-27b-Q8_K_XL",
      "object": "model",
      "owned_by": "local",
      "api": "responses",
      "context_length": 400000,
      "max_output_length": 128000,
      "input_modalities": ["text", "image"],
      "output_modalities": ["text"],
      "supported_features": ["tools", "reasoning", "vision"],
      "reasoning": {
        "default": "medium",
        "supported": ["low", "medium", "high", "xhigh"]
      }
    }
  ]
}
```

These map into OpenCode v2 as follows:

- `context_length` -> `limit.context`
- `max_input_length` -> `limit.input`
- `max_output_length` -> `limit.output`
- input/output modalities -> model capabilities
- `supported_features: ["tools"]` -> tool capability
- `reasoning.supported` -> native OpenCode reasoning variants
- `reasoning.default` -> default `reasoningEffort`

If a discovered model ID already exists elsewhere in OpenCode's catalog, the plugin can reuse known family, cost, release, and fallback metadata where the discovery response does not override it.

## Plugin options

Each entry in `options.providers` supports:

| Option | Required | Description |
| --- | --- | --- |
| `baseURL` | yes | HTTPS API base URL. `/models` is resolved relative to it. |
| `tls.certFile` | yes | PEM client certificate or certificate chain. |
| `tls.keyFile` | yes | PEM private key for the client certificate. |
| `tls.caFile` | no | PEM CA path, or an array of CA paths, used instead of Bun's normal trust store. |
| `tls.passphraseEnv` | no | Environment variable containing the private-key passphrase. |
| `tls.serverName` | no | Explicit TLS SNI/server-name override. |
| `name` | no | Display name for the provider. |
| `package` | no | Explicit native OpenCode provider package override. The old `@ai-sdk/openai` and `@ai-sdk/openai-compatible` values are migrated to their native equivalents. |
| `protocol` | no | `auto` (default), `responses`, or `chat-completions`. |
| `settings` | no | Additional native OpenCode provider settings. The bridge always owns `baseURL` and forces `transport: "http"`. |

Relative certificate paths resolve from OpenCode's process working directory. `~/...` is expanded to the current user's home directory.

If the server certificate chains to a normal public CA, omit `caFile`.

## Development

Requires Bun 1.4 or newer and OpenSSL for the integration tests.

```bash
bun install
bun run check
```

The test suite verifies mTLS authentication, protected loopback forwarding, SSE streaming, native provider selection, model discovery, and rich OpenCode model metadata mapping.
